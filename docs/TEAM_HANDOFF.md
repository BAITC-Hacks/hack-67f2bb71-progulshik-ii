# Работа команды из трёх человек

Проект: **AI Sana Challenge Hub**. Обязательный результат — работающий путь от короткого описания бизнес-задачи до публикации, отклика команды и ручного решения бизнеса. Репозиторий команды: https://github.com/BAITC-Hacks/hack-67f2bb71-progulshik-ii.

Основа проекта: сервер на Node.js и Express, сохранение в SQLite, общий API и независимый интерфейс на React + Vite. Для всех участников нужна Node.js версии 22.18 или новее. На момент передачи подготовлена серверная часть; интерфейс создают участники 2 и 3.

## Кто что делает

| Участник | Ответственность | Свои файлы |
| --- | --- | --- |
| 1 — владелец проекта | ИИ, рейтинг, сохранение, API, общие типы и клиент; объединение модулей; итоговая демонстрация | `backend/`, `shared/`, `scripts/`, `docs/`, корневые настройки и README |
| 2 | Основа интерфейса, переключение экранов и роли, создание и редактирование задачи, вопросы, подтверждение, рейтинг, публикация | `frontend/package.json`, настройки и зависимости `frontend/`, `frontend/src/App.jsx`, `frontend/src/main.jsx`, общие стили, `frontend/src/lib/`, `frontend/src/features/task-builder/` |
| 3 | Каталог и фильтры, просмотр опубликованной задачи, создание отклика, список предложений и ручное решение бизнеса | Только `frontend/src/features/catalog/` и `frontend/src/features/proposals/` |

Участники 2 и 3 не меняют сервер, `shared/`, корневой `package.json` и файлы друг друга. Если нужен новый метод API, они описывают его владельцу проекта. Общие изменения интерфейса, зависимости и подключение экранов делает участник 2. Участник 3 использует React и обычный CSS без добавления пакетов; CSS-классы имеют префикс `catalog-` или `proposals-`.

## Что сделать сейчас

1. Исходная версия серверной части находится в ветке `feature/backend-core`. Все начинают от этой ветки, а не от пустой `main`. Владелец проекта передаёт команде ссылку на неё.
2. Каждый скачивает репозиторий на свой компьютер. Для участника 2 используется ветка `feature/task-builder`, для участника 3 — `feature/catalog-proposals`.
3. Участник 2 создаёт приложение React + Vite с JavaScript/JSX **в папке `frontend/`**, добавляет основу приложения и временные экраны. Не запускает генератор поверх корня репозитория.
4. Участник 3 сразу пишет свои компоненты по контракту ниже, параллельно участнику 2. Для их запуска участник 2 передаёт ему первый коммит с основой `frontend/`. До получения этой основы участник 3 создаёт только файлы в своих двух папках, не добавляет настройки приложения.
5. Оба читают `docs/API.md`, `shared/types.ts` и `shared/api-client.js`. Сервер запускают по корневому README. Интерфейс работает на порту `5173`, сервер — на `3001`.
6. Через 60–90 минут участник 2 объединяет основу интерфейса со стартовыми экспортами участника 3. Затем команда рано проверяет весь путь пользователя и дорабатывает каждый свой модуль.
7. До конца оставляют минимум 45 минут на объединение, исправления и репетицию. Изменения передают через свои ветки; окончательное объединение в основную ветку делает владелец проекта.

Пока все приложения запускаются на разных компьютерах, у каждого своя локальная база. Для итоговой демонстрации весь сценарий запускают с одной общей версией проекта на компьютере владельца.

## Как соединяются экраны

Структура папок интерфейса:

```text
frontend/
  src/
    App.jsx
    lib/
      api-client.js
    features/
      task-builder/
        index.jsx
      catalog/
        index.jsx
      proposals/
        index.jsx
```

Участник 2 копирует готовый `shared/api-client.js` в `frontend/src/lib/api-client.js` без изменения публичных методов и создаёт один экземпляр: `createApiClient({ baseUrl: 'http://127.0.0.1:3001' })`. Один и тот же объект `api` передаётся компонентам через свойства. Методы и сигнатуры перечислены в `API.md` и готовом файле клиента. Если клиент обновлён владельцем проекта, участник 2 синхронизирует копию.

`App.jsx` хранит выбранный экран, идентификатор задачи и демонстрационную роль `role: 'business' | 'team'`. Достаточно переключения экранов состоянием React; отдельная библиотека маршрутизации для MVP не требуется.

| Файл и экспорт | Свойства | Что делает |
| --- | --- | --- |
| `task-builder/index.jsx`: `TaskBuilderPage` | `api`, `taskId?`, `onPublished(task)`, `onCancel()` | Создаёт или редактирует задачу. После успешной публикации передаёт полную задачу в `onPublished` |
| `catalog/index.jsx`: `CatalogPage` | `api`, `onOpenTask(taskId)`, `onCreateTask()` | Загружает каталог и фильтры; передаёт выбранный `id` в `onOpenTask` |
| `catalog/index.jsx`: `TaskDetailPage` | `api`, `taskId`, `role`, `onBack()`, `onEdit(taskId)?` | Загружает задачу, показывает полную карточку и `ProposalsPanel`; в роли бизнеса предлагает редактирование через `onEdit` |
| `proposals/index.jsx`: `ProposalsPanel` | `api`, `taskId`, `role` | В роли команды показывает форму отклика; в роли бизнеса — отклики с ручным выбором |

Используются **именованные экспорты**. `taskId` — строка от API; `task` — объект `BusinessTask` из общих типов. Свойство `api` — экземпляр общего клиента. В компонентах участника 3 нет глобального хранилища, самостоятельной маршрутизации или импортов из `task-builder/`.

Пример подключения участником 2:

```jsx
import { TaskBuilderPage } from './features/task-builder/index.jsx';
import { CatalogPage, TaskDetailPage } from './features/catalog/index.jsx';
import { createApiClient } from './lib/api-client.js';

const api = createApiClient({ baseUrl: 'http://127.0.0.1:3001' });

// activeId и screen — состояние App.
<CatalogPage
  api={api}
  onOpenTask={(id) => { setActiveId(id); setScreen('details'); }}
  onCreateTask={() => { setActiveId(null); setScreen('builder'); }}
/>

<TaskDetailPage
  api={api}
  taskId={activeId}
  role={role}
  onBack={() => setScreen('catalog')}
  onEdit={(id) => { setActiveId(id); setScreen('builder'); }}
/>

<TaskBuilderPage
  api={api}
  taskId={activeId || undefined}
  onCancel={() => setScreen('catalog')}
  onPublished={(task) => { setActiveId(task.id); setScreen('details'); }}
/>
```

Это примеры отдельных экранов: `App` отображает нужный по значению `screen`, а не все одновременно. Пока модуль коллеги не готов, участник 2 использует заглушку внутри `App.jsx`, не создавая файлы в папках участника 3.

## Правила продукта, которые должны совпадать во всех модулях

- Рейтинг берётся из ответа сервера. Критерии, недостающие поля и рекомендации отображаются рядом с суммой баллов.
- `status: 'draft'` — непубличный черновик; `rating.level: 'draft'` — низкая готовность. Эти значения нельзя смешивать.
- Опубликованные задачи доступны независимо от рейтинга. Форма отклика доступна и при 0–39 баллах.
- Анализ ИИ возвращает предложение и вопросы, ничего не сохраняет. Сохранение, подтверждение человеком и публикация — отдельные действия.
- Изменённые поля карточки теряют подтверждение. Изменение исходного описания снимает все подтверждения. После изменения опубликованной задачи требуется повторная публикация.
- В каждом запросе изменения задачи используется свежая `revision`. При `409` нужно получить актуальную задачу и сверить изменения.
- Отклики отправляются от существующей команды и содержат обязательную ссылку HTTP(S). Пользователь бизнеса может принять несколько откликов. Принятие одного не закрывает остальные.
- Названия, контакты и результаты ИИ пользователь проверяет перед подтверждением. Неизвестные сведения остаются пустыми.
- Загруженные и добавленные сведения берутся из сервера. Массивы примеров внутри React не заменяют реальные запросы.

## Что показать за пять минут

1. В роли бизнеса ввести слабое описание задачи; показать низкую готовность.
2. Получить уточняющие вопросы, ответить на них и отредактировать карточку.
3. Подтвердить проверенные сведения; показать рост рейтинга и объяснение баллов.
4. Опубликовать задачу и найти её в каталоге.
5. В роли команды отправить предложение.
6. В роли бизнеса открыть отклики и вручную принять одно предложение.

В README итоговой версии должны быть команды запуска сервера и интерфейса, описание деморежима ИИ, формула рейтинга и известные ограничения. За это после объединения отвечает владелец проекта.
