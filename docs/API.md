# API для интерфейса AI Sana Challenge Hub

Базовый адрес локального сервера: `http://127.0.0.1:3001`. Все запросы и ответы используют JSON. Для тела запроса передавайте `Content-Type: application/json`. Запуск сервера описан в корневом README.

Общие типы находятся в `shared/types.ts`, готовый клиент — в `shared/api-client.js`. Идентификаторы приходят от сервера: не задавайте их в интерфейсе вручную. Демо работает без регистрации и проверки прав; переключатель «Бизнес / Команда» меняет экран интерфейса.

## Готовый JavaScript-клиент

```js
import { createApiClient, ApiRequestError } from './api-client.js';

const api = createApiClient({ baseUrl: 'http://127.0.0.1:3001' });
const { items } = await api.listTasks({ status: 'published' });
```

Методы возвращают тела ответов из таблиц ниже; результаты списков нужно читать через `result.items`.

| Метод клиента | Действие |
| --- | --- |
| `api.health()` | Доступность сервера |
| `api.rubric()` | Критерии рейтинга, подписи и уровни готовности |
| `api.listTasks(filters = {})` | Список задач `{ items }` |
| `api.getTask(id)` | Одна задача |
| `api.createTask(input)` | Новый черновик |
| `api.updateTask(id, { revision, ...patch })` | Изменение задачи |
| `api.confirmTask(id, { revision, fields })` | Подтверждение просмотренных полей |
| `api.publishTask(id, { revision })` | Публикация |
| `api.analyzeTask(input)` | Анализ ИИ без сохранения |
| `api.listTeams()` | Команды `{ items }` |
| `api.createTeam(input)` | Новая команда |
| `api.listProposals(taskId)` | Отклики `{ items }` |
| `api.listAllProposals({ taskId?, teamId? })` | Общий список или отклики выбранной задачи/команды `{ items }` |
| `api.createProposal(taskId, input)` | Новый отклик |
| `api.decideProposal(id, status)` | Ручное решение: строка `'accepted'` или `'rejected'` |

При ошибках клиент выбрасывает `ApiRequestError` с `message`, `status`, `code`, `details`. В обработчике используйте `error.message`; конфликт ревизии проверяйте через `error.status === 409`.

## Поля карточки

`Card` — объект из десяти строк. Отсутствие сведений обозначается пустой строкой, а не выдуманным значением.

| Ключ | Содержание |
| --- | --- |
| `title` | Название задачи |
| `context` | Что происходит сейчас |
| `need` | Что необходимо изменить |
| `users` | Для кого создаётся решение |
| `data` | Доступные данные, материалы, примеры, источники |
| `constraints` | Сроки, технологии, доступы и другие ограничения |
| `expectedResult` | Результат, который должна представить команда |
| `successCriteria` | Измеримые критерии приёмки |
| `contact` | Контакт представителя бизнеса |
| `interactionFormat` | Формат консультаций и обратной связи |

Каждое поле содержит максимум 6000 символов. В `card` и `answers` запросов можно передавать только изменившиеся поля. Сервер удаляет пробелы по краям строк. Неизвестные ключи тела запроса не допускаются.

## Задача и рейтинг

Ответ с задачей соответствует `BusinessTask`:

```ts
{
  id: string,
  rawDescription: string,
  topic: string,
  card: Card,
  confirmedFields: CardField[],
  status: 'draft' | 'published',
  revision: number,
  createdAt: string,
  updatedAt: string,
  publishedAt: string | null,
  rating: {
    score: number,
    level: 'draft' | 'working' | 'ready' | 'priority',
    label: string,
    breakdown: ScoreCriterion[],
    missingFields: CardField[],
    unconfirmedFields: CardField[],
    recommendations: string[]
  }
}
```

`ScoreCriterion` содержит `id`, `label`, `maxPoints`, `points`, `fields`, `missingFields`, `unconfirmedFields`, `explanation`. Показывайте готовые `rating.score`, `rating.breakdown` и `rating.recommendations` из ответа сервера. Повторный расчёт формулы в интерфейсе не нужен.

Баллы даются только за заполненные **и подтверждённые человеком** поля. Поле должно содержать хотя бы букву или цифру; ответы `tbd`, `todo`, `не знаю`, `не указано`, `неизвестно` считаются отсутствием сведений и не подтверждаются. Для неизвестного значения оставляйте пустую строку.

Распределение баллов:

| Группа | Баллы |
| --- | ---: |
| Контекст и потребность | 20: по 10 за `context` и `need` |
| Данные и материалы | 20 за `data` |
| Ожидаемый результат | 15 за `expectedResult` |
| Критерии успеха | 15 за `successCriteria` |
| Ограничения | 10 за `constraints` |
| Пользователи | 10 за `users` |
| Связь с бизнесом | 10: по 5 за `contact` и `interactionFormat` |

`title` не добавляет баллы, но необходим для публикации. Рейтинг измеряет полноту подтверждённых сведений; он не гарантирует правильность или реализуемость задачи.

| `rating.level` | Баллы | Значение |
| --- | ---: | --- |
| `draft` | 0–39 | Требует уточнения |
| `working` | 40–69 | Рабочая |
| `ready` | 70–89 | Готовая |
| `priority` | 90–100 | Приоритетная |

**`status` и `rating.level` независимы.** Опубликованная задача может иметь `rating.level: 'draft'`. Она остаётся видимой в каталоге и принимает отклики. Не скрывайте задачи и не блокируйте отклики из-за низкого рейтинга.

## Методы задач

| Метод | Адрес | Тело / параметры | Ответ |
| --- | --- | --- | --- |
| `POST` | `/api/tasks` | `{ rawDescription, topic?, card?, interview? }` | `BusinessTask` |
| `GET` | `/api/tasks` | Параметры описаны ниже | `{ items: BusinessTask[] }` |
| `GET` | `/api/tasks/:id` | — | `BusinessTask` |
| `PATCH` | `/api/tasks/:id` | `{ revision, card?, topic?, rawDescription?, interview? }` | `BusinessTask` |
| `POST` | `/api/tasks/:id/confirm` | `{ revision, fields: CardField[] }` | `BusinessTask` |
| `POST` | `/api/tasks/:id/publish` | `{ revision }` | `BusinessTask` |

`rawDescription`: 10–12000 символов. `topic`: 1–100 символов, при создании по умолчанию `Другое`. Создание задачи сохраняет черновик. В `PATCH` передайте хотя бы одно из `card`, `topic`, `rawDescription`, `interview` вместе с актуальной ревизией.

`interview` сохраняет уточнение до формирования карточки: `{ source, questions, answers }`. `source` — описание, по которому построены вопросы (до 12000 символов). `questions` содержит 0 либо 3–20 объектов `{ id, field, text, hint }`: уникальный `id` до 100 символов, `field` из `CardField`, `text` и `hint` до 800 символов. `answers` — объект `{ questionId: "ответ" }`, каждый ответ до 6000 символов и только для сохранённого вопроса. Интервью возвращается в `BusinessTask`; старые записи могут не иметь его. Изменение только интервью увеличивает ревизию, но не снимает публикацию и не меняет баллы: для этого нужно перенести ответы в карточку и подтвердить её. При изменении исходного описания без нового `interview` старое интервью очищается.

Параметры каталога:

- `status=published|draft|all`; по умолчанию `published`;
- `topic=<тема>` — точное совпадение;
- `level=draft|working|ready|priority` — фильтр по готовности, а не по публикации;
- `q=<поисковая строка>` — поиск без учёта регистра в названии, исходном описании, контексте и потребности.

Каталог сортируется по убыванию рейтинга; при одинаковом рейтинге сначала идут недавно изменённые задачи. Пример: `/api/tasks?status=published&level=ready`.

### Подтверждение, редактирование и публикация

Сначала сохраните изменения через `PATCH`, затем показывайте пользователю сохранённую карточку для проверки. Кнопка или флажки подтверждения должны отражать реальное действие человека. В `/confirm` отправляйте только просмотренные непустые поля; массив содержит от 1 до 10 элементов.

Изменение содержимого поля карточки снимает подтверждение именно этого поля. Изменение исходного `rawDescription` снимает подтверждения всей карточки, поскольку меняется источник сведений. После правок карточки, описания или темы опубликованная задача возвращается в черновик: для возвращения в каталог её нужно снова подтвердить и опубликовать. Запрос без фактических изменений возвращает прежнюю задачу.

Публикация требует непустого названия и подтверждения всех полей, которые считаются заполненными. Пустые сведения и типовые заглушки вроде «не знаю» не требуют подтверждения и не дают баллов. Минимального порога рейтинга для публикации нет.

Каждая изменяющая задача операция использует `revision` из последнего ответа. После ответа заменяйте локальную задачу полученным объектом целиком. Не рассчитывайте новую ревизию самостоятельно.

Если два окна редактировали одну задачу, устаревшая ревизия приводит к HTTP `409`. Загрузите свежую задачу, сохраните введённый человеком текст отдельно и предложите сверить изменения. Не повторяйте запрос бесконечно и не подставляйте новую ревизию без просмотра актуальных данных.

## ИИ: анализ описания

`POST /api/ai/analyze`

```json
{
  "rawDescription": "Нужен помощник для разбора обращений нашей учебной организации.",
  "card": {
    "users": "Сотрудники приёмной комиссии"
  },
  "answers": {
    "data": "Есть 200 обезличенных обращений в CSV"
  }
}
```

`card` — текущие сведения, `answers` — ответы человека, записанные по ключам карточки. Эти объекты необязательны. Ответ соответствует `AiAnalysis`:

```ts
{
  mode: 'mock' | 'openai' | 'fallback',
  questions: Array<{ field: CardField, question: string, reason: string }>,
  suggestedCard: Card,
  missingFields: CardField[],
  warnings: string[]
}
```

Отобразите уточняющие вопросы и предложенную карточку для редактирования. Ответ человека на вопрос связывайте с его `field`. `warnings` показывайте понятным текстом. `mode` позволяет объяснить, использовался ли живой ИИ, демонстрационный режим или запасной сценарий после ошибки внешнего сервиса.

**Анализ не сохраняет, не подтверждает и не публикует задачу.** Для сохранения принятого человеком предложения вызовите `PATCH /api/tasks/:id` с `card: suggestedCard`, либо создайте черновик через `POST /api/tasks`. После этого отдельно получите подтверждение человека. Не вызывайте `/confirm` автоматически при получении ответа ИИ.

При недоступности внешнего API запасная логика позволяет продолжить демонстрацию. Неизвестные сведения должны оставаться пустыми. Если предложенные значения сомнительны, пользователь может исправить их до подтверждения.

## Команды

| Метод | Адрес | Тело | Ответ |
| --- | --- | --- | --- |
| `GET` | `/api/teams` | — | `{ items: Team[] }` |
| `POST` | `/api/teams` | `{ name, interests?, skills?, technologies? }` | `Team` |

`Team` содержит `id`, `name`, `interests`, `skills`, `technologies`. Название — 2–120 символов. Последние три поля — массивы строк: максимум 20 элементов, каждый длиной 1–100 символов. При создании по умолчанию это пустые массивы. Для быстрого демо достаточно выбрать один из загруженных профилей.

## Отклики и выбор бизнеса

| Метод | Адрес | Тело | Ответ |
| --- | --- | --- | --- |
| `GET` | `/api/tasks/:id/proposals` | — | `{ items: Proposal[] }` |
| `GET` | `/api/proposals` | Необязательные `taskId`, `teamId` | `{ items: Proposal[] }` |
| `POST` | `/api/tasks/:id/proposals` | `{ teamId, idea, plan, timeline, prototypeUrl }` | `Proposal` |
| `PATCH` | `/api/proposals/:id` | `{ status: 'accepted' | 'rejected' }` | `Proposal` |

```ts
{
  id: string,
  taskId: string,
  teamId: string,
  idea: string,
  plan: string,
  timeline: string,
  prototypeUrl: string,
  status: 'pending' | 'accepted' | 'rejected',
  createdAt: string,
  updatedAt: string
}
```

`idea` и `plan`: 10–6000 символов каждый. `timeline`: 2–500 символов. `prototypeUrl` обязателен: ссылка `http://` / `https://`, максимум 2048 символов. `teamId` должен ссылаться на существующую команду.

Отклики создаются для опубликованной задачи. Новому отклику сервер присваивает `pending`. Число откликов не ограничено; низкий рейтинг задачи не мешает откликнуться. Для имени команды сопоставляйте `proposal.teamId` с объектами из `/api/teams`.

Бизнес выбирает вручную одну, несколько или ни одной команды. При принятии одного отклика не отклоняйте остальные автоматически. Отправляйте изменение статуса только после нажатия пользователем соответствующей кнопки.

## Ошибки и состояние сервера

`GET /api/health` — проверка доступности сервера.

```json
{ "status": "ok", "service": "ai-sana-challenge-hub", "aiMode": "mock" }
```

`GET /api/rubric` — критерии рейтинга, подписи полей и уровни готовности для отображения в интерфейсе.

Ошибки API имеют общую структуру:

```json
{
  "error": {
    "code": "КОД_ОШИБКИ",
    "message": "Понятное описание ошибки",
    "details": {}
  }
}
```

`details` может отсутствовать. На экране показывайте `error.message`. Ошибка сети, когда сервер недоступен, может не иметь JSON-ответа: для неё нужен отдельный текст и возможность повторить действие. Во время запроса отключайте повторное нажатие кнопки.

| HTTP | `error.code` | Как обработать |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Показать ошибочные поля из `details`: массив `{ field, message }` |
| 400 | `INVALID_FILTER`, `INVALID_JSON` | Исправить параметры запроса |
| 400 | `EMPTY_FIELDS` | Не подтверждать пустые сведения или заглушки |
| 400 | `TITLE_REQUIRED` | Предложить заполнить название |
| 400 | `CONFIRMATION_REQUIRED` | Показать неподтверждённые поля из `details.fields` |
| 400 | `TASK_NOT_PUBLISHED` | Для отправки отклика нужна опубликованная задача |
| 404 | `NOT_FOUND` | Запись или адрес не найдены |
| 409 | `REVISION_CONFLICT` | Загрузить актуальную задачу; `details.currentRevision` содержит новую ревизию |
| 413 | `BODY_TOO_LARGE` | Размер тела запроса превышает 128 КБ |
| 500 | `INTERNAL_ERROR` | Показать сообщение и предложить повторить действие |

## Настройка ИИ через интерфейс

Эти маршруты доступны только на loopback-адресе локального сервера с именем `localhost`, `127.0.0.1` или `[::1]`. Для изменяющих запросов требуется `Origin`, совпадающий с адресом приложения, JSON и заголовок `X-AI-Settings: local`. Интерфейс отправляет их сам. Ответы не кешируются и никогда не содержат ключ.

| Метод | Адрес | Тело | Ответ |
| --- | --- | --- | --- |
| `GET` | `/api/ai/settings` | — | Текущее состояние |
| `POST` | `/api/ai/settings` | `{ apiKey?, model? }` | Состояние после успешной проверки |
| `POST` | `/api/ai/settings/demo` | `{}` | Деморежим, активный ключ очищен |

Состояние: `{ mode, model, keyConfigured, source, verified, checking }`. `source` — `environment`, `session` или `none`; `verified` означает успешный последний анализ/проверку текущей настройки, а не гарантию будущей доступности сервиса. Пустой/отсутствующий `apiKey` использует уже настроенный ключ, если он есть. Название модели ограничено 100 символами; ключ — 1024 ASCII-символами без пробелов и переносов.

Подключение выполняет один анализ вымышленного примера через OpenAI и расходует API-кредиты. Новый ключ и модель становятся активными только после корректного ответа `openai`; при ошибке прежняя настройка остаётся. Настройка общая для вкладок этого сервера и хранится только в памяти процесса. `.env` не меняется: после перезапуска используются настройки запуска.

Безопасные ошибки: `INVALID_AI_SETTINGS` / `AI_KEY_REQUIRED` (400), `LOCAL_SETTINGS_ONLY` (403), `AI_SETTINGS_BUSY` (409), `AI_CONNECTION_FAILED` (422), `AI_SETTINGS_UNAVAILABLE` (503). Ответы не содержат тело ошибки провайдера, присланный ключ или другие секреты.

## Данные демонстрации

При первом запуске с `SEED_DEMO=true` база SQLite наполняется демонстрационными данными: минимум 5 черновиков задач, 5 опубликованных карточек, 5 команд и 5 откликов. Используйте полученные от API идентификаторы. Путь к базе задаётся через `DATABASE_PATH`; данные остаются после перезапуска сервера.

## Порядок основного сценария

1. `POST /api/tasks` — сохранить исходное описание и получить `id`, `revision`.
2. `POST /api/ai/analyze` — получить вопросы и предложение карточки.
3. Показать вопросы, собрать ответы; при необходимости снова вызвать анализ с `answers`.
4. Дать человеку отредактировать карточку, затем `PATCH /api/tasks/:id`.
5. После явной проверки человеком вызвать `/confirm` и показать выросший рейтинг.
6. По нажатию «Опубликовать» вызвать `/publish`.
7. Получить каталог, открыть опубликованную задачу, отправить отклик выбранной команды.
8. Переключить демонстрационную роль на бизнес и вручную принять или отклонить отклик.

После каждого изменяющего запроса используйте объект из ответа и его актуальную `revision`.
